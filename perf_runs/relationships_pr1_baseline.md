## Definition-count sweep (S0)

| Definitions | Queries |
|---|---|
| 5 | 5 |
| 25 | 25 |

Exactly one association query per definition, confirming the definition-centric access pattern the effort exists to
replace. `RelationshipDefinitionSweepTest` asserts these values, and asserts that the object really has only the
fixture's definitions — definitions apply model-wide, so a stray definition would inflate the low end of the sweep
without any visible symptom.

## Findings

**Query count scales with definition count, one-for-one.** The S0 sweep is unambiguous: 5 definitions cost 5
queries, 25 cost 25. This is TRD acceptance criterion 1 in its current, failing state.

**List views are the worst surface by an order of magnitude.** A single table row with relationship columns visible
costs 2183 queries, because `RelationshipColumn` reads the `associations` property (2 queries per row) and then
resolves each association's peer through its GenericForeignKey. The table's automatic prefetch logic skips it
because `associations` is a Python property rather than a model field. The TRD's caller list does not mention list
views; on this evidence they belong in it.

**At high association counts the problem stops being query count.** S3 renders the detail panels in only 30
queries but spends 1934 ms in the database — 200× the S1 figure for 100× the associations. `get_relationships_with_related_objects()`
issues one reverse-generic-join-with-`DISTINCT` per definition, and those joins get expensive on their own. By
contrast `get_relationships_data()` at the same size costs 6.25 ms, because it counts association rows instead of
joining to peers. **Bulk peer resolution (PR 3) must be measured on database time, not query count, or its main
benefit at scale will be invisible.**

**REST relationship serialization is opt-in and costly.** `?include=relationships` on a single object costs 237
queries at S1, because `RelationshipsDataField.to_representation()` calls `association.get_peer()` twice per
association. Without the `include` parameter the API does no relationship work at all — an early version of these
tests measured 7 queries and would have reported a false baseline.

## Index query plans

Captured against 41,508 association rows across ~2,500 objects: one "heavy" object holding 10,000 associations and
a "typical" object holding 20. Generated with
`nautobot-server generate_relationship_test_data --scenario S3` plus three `--scenario S4 --objects 500` runs.

### Typical object, source-side lookup

Before (migration 0145):

```
Bitmap Heap Scan on extras_relationshipassociation  (cost=4.32..19.32 rows=3) (actual time=0.008..0.017 rows=13)
  Recheck Cond: (source_id = '...'::uuid)
  Filter: (source_type_id = 15)
  Heap Blocks: exact=13
  Buffers: shared hit=15
  ->  Bitmap Index Scan on extras_relationshipassociation_source_id_cb8931c1  (cost=0.00..4.32 rows=4)
        Index Cond: (source_id = '...'::uuid)
```

After (migration 0146):

```
Index Scan using relassoc_src_obj_rel_idx on extras_relationshipassociation  (cost=0.41..15.52 rows=3) (actual time=0.063..0.080 rows=13)
  Index Cond: ((source_type_id = 15) AND (source_id = '...'::uuid))
  Buffers: shared hit=13 read=3
```

The plan class improves from a bitmap heap scan to a plain index scan, and the `source_type_id` recheck filter
disappears because both columns are now in the index condition. The destination-side lookup behaves identically
(`relassoc_dst_obj_rel_idx`, cost 11.96 → 8.43).

### Heavy object, source-side lookup

Still a bitmap heap scan after the change, which is correct — 5,772 matching rows is 14% of the table — but the
recheck filter on `source_type_id` is gone and the estimate improves slightly (cost 693.70 → 679.21).

### Verdict on the indexes

Ship them: the plans genuinely improve, no sequential scan appears where an indexed lookup is expected, and the
`source_type_id` recheck is eliminated on both sides. But be clear about the size of the win — every plan here
executes in well under a millisecond either way, and at this scale the indexes are not what makes relationship
retrieval slow. **The query-count and database-time reductions in the following PRs are where the latency is.**

Note also that the two relationship-leading index candidates from the technical requirements were dropped without
measurement: migration `0003_initial_part_3` already creates
`unique_together = (relationship, source_type, source_id, destination_type, destination_id)`, whose leading prefix
is exactly the proposed `relassoc_rel_src_obj_idx`. Adding it would have duplicated an existing index.

## Reproducing

```bash
# Query counts and timings for S0, S1, S4 (fast)
NAUTOBOT_RELATIONSHIP_BENCH_OUT=perf_runs/relationships_pr1_baseline.jsonl \
  invoke tests --skip-docs-build --label nautobot.extras.tests.test_relationship_performance

# Add S2 and S3 (slow: S3 creates 10,000 associations)
NAUTOBOT_RELATIONSHIP_BENCH_FULL=True \
NAUTOBOT_RELATIONSHIP_BENCH_OUT=perf_runs/relationships_pr1_baseline.jsonl \
  invoke tests --skip-docs-build --label nautobot.extras.tests.test_relationship_performance

# Query plans against a development database
invoke cli -c "nautobot-server generate_relationship_test_data --scenario S3 --seed explain --flush --print-explain"
```
